## Overview and stack

Notette is a single SvelteKit (Svelte 5, TypeScript) application that serves four things from one deployment: the admin dashboard (`src/routes/(app)`), the auth pages (`src/routes/(auth)`, `(popup)`), the JSON API used by the widget (`src/routes/api/widget/[key]/…`), and the compiled standalone widget bundle (`GET /notette.js`). Data lives in PostgreSQL via Drizzle ORM; screenshots live on a local filesystem volume behind a storage abstraction. `@sveltejs/adapter-node` produces the production server in `build/`, packaged by the Dockerfile with PostgreSQL in `docker-compose.yml`.

Key directories:

- `src/lib/server/` — everything server-only: `db/` (schema, client, migrations), `auth/` (passwords, sessions, cookies, bootstrap admin), `services/` (users, projects, members, feedback, comments, uploads, auth-requests, notifications, mentions, email-verification), `email/` (SMTP mailer, templates, digest builder), `storage/`, `origins.ts` (CORS allow-list), `rate-limit.ts`, `http.ts` (API error helpers, `requireAdmin`/`adminUser`), `validation.ts` (zod schemas), `turnstile.ts` + `turnstile-verify.ts` (bot protection), `widget-cors.ts`, `widget-access.ts` (sign-in requirement), `widget-thread.ts`, `widget-viewer.ts` (viewer DTO with notification preference).
- `src/lib/shared/` — framework-free code used by both the server/dashboard and the widget: `types.ts` (DTOs and the feedback payload), `roles.ts` (`UserRole`, `isAdminRole`), `turnstile-client.ts` (Turnstile script loader), `mentions.ts` (@-mention parsing/matching) and `agent-format.ts` (Copy for Agent).
- `src/lib/components/`, `src/lib/format.ts`, `src/lib/embed.ts` — dashboard UI helpers. `MentionTextarea.svelte` and `MentionText.svelte` there are shared with the widget (styled through CSS variables of either design system).
- `src/widget/` — the widget (see *Widget*).
- `drizzle/` — generated SQL migrations. `scripts/reset-password.mjs` — admin recovery.

The package manager is pnpm (version pinned via `packageManager` in `package.json`; `pnpm-lock.yaml` is the only lockfile). Verification commands: `pnpm run check` (svelte-check across app + widget), `pnpm test` (vitest; DOM tests use jsdom), `pnpm run build`. The Docker CI job builds the image.

## Data layer

Schema: `src/lib/server/db/schema.ts`. Tables: `users` (role `owner|admin|member`, see *Roles and project access*; `email_verified_at`, null only for unconfirmed widget sign-ups), `projects` (client key, `allowed_origins` jsonb array, visibility/reply/screenshot flags, `anonymous_feedback_allowed`, `open_signups`, `email_verification_required`, `feedback_seq` counter), `project_members` (composite PK `project_id + user_id`, `added_by_id`; which members may use a project), `sessions` (id = SHA-256 of the raw token, `kind` `dashboard|widget`, widget sessions carry `project_id` + `origin`), `auth_requests` (widget sign-in handshake), `feedback` (thread root with all captured context; `number` is per-project sequential, allocated by incrementing `projects.feedback_seq` inside a transaction; `user_id` is set for any signed-in author; `mentions` jsonb `{ id, name }[]`), `comments` (replies, also with `mentions`), `uploads` (screenshots; `feedback_id` cascade), `email_verifications` (hashed confirmation tokens), `notification_mutes` (per user and project opt-out) and `notifications` (email outbox), see *Email, notifications and mentions*.

Feedback and comment rows are read with a left join on `users` so DTOs carry the author's *current* role (`authorRole` on `FeedbackRow`/`CommentRow` → `isAdmin`/`isMember` in the DTOs); a deleted account degrades to anonymous. `services/projects.ts` selects `getTableColumns(projects)` plus the count subqueries, so new project columns need no query changes.

Migrations are generated with `pnpm run db:generate` (drizzle-kit, config in `drizzle.config.ts`) into `drizzle/` and applied at startup by `runMigrations()` (`src/lib/server/db/migrate.ts`) from the `init` hook in `src/hooks.server.ts` unless `NOTETTE_AUTO_MIGRATE=false`. Before migrating, `waitForDatabase()` retries the connection for up to about a minute so the app container survives PostgreSQL still booting; any other error aborts startup. Never edit generated SQL by hand after it has shipped; add a new migration instead. Every schema change must ship with its generated migration in the same change.

`src/lib/server/db/index.ts` exports `db`, a Proxy that creates the pooled `postgres` client from `DATABASE_URL` on first use. Keep it lazy: SvelteKit's post-build route analysis imports server modules inside the Docker build where no `DATABASE_URL` exists, and an eager client would abort `pnpm run build`. Unit tests must not import modules that pull the db in transitively (keep pure helpers like `origins.ts`, `password.ts`, `agent-format.ts` free of db imports).

## Configuration

`src/lib/server/env.ts` exposes `config` with lazy getters over `$env/dynamic/private` so the same image is configured at runtime. Add new variables there, in `.env.example`, `docker-compose.yml` and the README table. `NOTETTE_URL` (normalised, no trailing slash) is the public base URL used for embed snippets, authorize URLs and absolute screenshot links (`src/lib/server/base-url.ts` falls back to the request origin). `TURNSTILE_SITE_KEY`/`TURNSTILE_SECRET_KEY` enable bot protection only when both are set (`config.turnstileEnabled`, see *Bot protection*). `SMTP_HOST` + `EMAIL_FROM` (plus `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `NOTETTE_EMAIL_BATCH_SECONDS`) enable outgoing email (`config.emailEnabled`, see *Email, notifications and mentions*).

## Authentication and sessions

Passwords: scrypt via Node's `crypto` (`src/lib/server/auth/password.ts`, format `scrypt$N$r$p$salt$hash`; `scripts/reset-password.mjs` duplicates the algorithm and must stay in sync). Minimum length 10.

Sessions (`src/lib/server/auth/sessions.ts`): random 32-byte tokens with prefixes `nts_` (dashboard) / `ntw_` (widget); only the SHA-256 is stored. Sliding expiry (`NOTETTE_SESSION_DAYS`), `last_used_at` throttled to one write per 5 minutes. Dashboard sessions ride in the `notette_session` httpOnly SameSite=Lax cookie (secure when the request is HTTPS). Widget sessions are bearer tokens bound to one project and one origin; `hooks.server.ts` only honours them on `/api/widget/*` and only when the request origin matches the session origin. Cookies are ignored on widget routes and bearer tokens are ignored elsewhere, which keeps CSRF concerns confined to form actions (protected by SvelteKit's origin check) and makes third-party cookies unnecessary.

Widget sign-in has two paths, both ending in a widget session:

1. **Inline** (`POST api/widget/[key]/auth/login` and `auth/signup`, schemas `widgetLoginSchema`/`widgetSignupSchema`): the widget's `AuthDialog` posts email + password (plus a Turnstile token when configured) straight to the widget API from the allowed origin and stores the returned bearer token. Sign-up is only accepted when `project.openSignups` is on; it creates a `member` account, adds it to the project and signs it in, unless the project requires email verification, in which case it answers 202 with `verificationRequired` and the account cannot sign in until the emailed link is opened (see *Email, notifications and mentions*). Login (widget and dashboard) rejects unverified accounts with `email_unverified`. Login is rate limited per IP (10 / 15 min), sign-up 5 / hour, verification resends 5 / 15 min.
2. **Dashboard approval** (`src/lib/server/services/auth-requests.ts`, routes under `api/widget/[key]/auth/requests`): the widget generates a UUID request id and a random poll secret, opens `NOTETTE_URL/widget/authorize?request=<id>` synchronously in the click handler (popup blockers), then POSTs the id + secret (hash stored) from the allowed origin. The authorize page (`src/routes/(popup)/widget/authorize`) requires a dashboard login, checks project access for members (state `no_access`), and shows the requesting origin/project; approving creates a widget session and parks the raw token on the request row. The widget polls `…/auth/requests/<id>/poll` with the secret every 1.5 s for up to 10 minutes; the token is returned exactly once and the row deleted. Expired approved-but-unclaimed requests delete their session during hourly maintenance. Nothing depends on `window.opener`/`postMessage`, so COOP-isolated host pages and blocked popups (fallback link) both work.

`locals.user` is any authenticated user; `toViewerDto()` (`services/users.ts`) turns it into the `WidgetViewerDto` (`admin`, `role`, `name`, `email`, `emailNotifications`); `widgetViewer(user, projectId)` (`widget-viewer.ts`) fills in the per-project notification preference and is what config, login, signup and poll return.

First admin: `/setup` (only while `users` is empty) or `NOTETTE_ADMIN_EMAIL`/`PASSWORD` bootstrap (`src/lib/server/auth/bootstrap.ts`, never modifies existing users).

## Roles and project access

Roles live in `src/lib/shared/roles.ts` (`UserRole`, `isAdminRole`), shared by server, dashboard and widget:

- `owner` — everything, including user management (the last owner cannot be demoted or deleted).
- `admin` — manage projects and triage feedback in the dashboard and the widget.
- `member` — a reviewer account. Only the widget (on projects they have access to) plus a minimal dashboard: `/` lists their projects and `/settings/account` manages profile, password and sessions; every other `(app)` route returns 403 (`MEMBER_PATHS` in `src/routes/(app)/+layout.server.ts`). Members are *reviewers* for the purposes of `publicFeedbackVisible` and `reviewerRepliesEnabled`; only admins bypass those.

Per-project flags (`projects` table, form fields parsed in `src/lib/server/project-form.ts`):

- `anonymousFeedbackAllowed` (default on) — when off, every widget route except `config` and `auth/*` rejects anonymous requests with 401 `sign_in_required` (`requireWidgetViewer` in `src/lib/server/widget-access.ts`; `loadWidgetThread` calls it too). The widget then opens the sign-in dialog instead of the toolbar.
- `openSignups` (default off) — anyone can sign up from the widget, and any signed-in account is added to the project on first access.

The single access rule is `ensureProjectAccess(user, project)` in `src/lib/server/services/members.ts`: admins always pass; members pass when a `project_members` row exists, or when the project is open (the row is inserted then); otherwise false. It runs in `hooks.server.ts` for every bearer-authenticated widget request (a failing session is invalidated, so revoking access takes effect immediately), on inline login, on dashboard approval, and for `/uploads/[id]`. `removeProjectMember` also deletes the user's widget sessions for that project. Admin-only API actions use `requireAdmin()`; code that needs "admin or null" uses `adminUser()` (both in `http.ts`).

Dashboard management: owners create users of any role under *Settings → Users*; the project settings page has a *Members* card (`addMember` existing member accounts, `createMember` creates a member account inline, `removeMember`) available to admins and owners.

## Bot protection

Optional Cloudflare Turnstile. `src/lib/server/turnstile-verify.ts` is the pure siteverify client (unit-tested with an injected `fetch`; a bad secret or Cloudflare outage is reported as `unavailable`, which becomes a 503 rather than blaming the user). `src/lib/server/turnstile.ts` wires it to `config`: `requireTurnstile(event, token)` is a no-op when the keys are unset and otherwise throws an `ApiError` (400 `turnstile_failed` / 503 `turnstile_unavailable`). It is applied to anonymous feedback creation and replies (signed-in users skip it), widget login/sign-up, and the dashboard login form action (field `cf-turnstile-response`). The widget learns the site key from `GET config` (`turnstileSiteKey`).

Client side, `src/lib/shared/turnstile-client.ts` loads `challenges.cloudflare.com/turnstile/v0/api.js?render=explicit` once and returns the global API; the widget's `Turnstile.svelte` and the login page render explicitly into an element (works inside the shadow root) with `appearance: 'interaction-only'` and `size: 'flexible'` (containers must be ≥ 300 px wide). Tokens are single-use, so every form calls `reset()` after a failed attempt (and after successful replies). The dashboard CSP (`svelte.config.js`) allows `https://challenges.cloudflare.com` in `script-src` and `frame-src`; host sites embedding the widget must do the same in their own CSP when Turnstile is enabled.

## Widget API

All widget traffic goes through `/api/widget/[clientKey]/…`. `src/hooks.server.ts` (`widgetApi` handle) resolves the project by key, determines the request origin (`Origin` header, falling back to `Referer`), matches it against the project's allow-list (`src/lib/server/origins.ts`: exact origins, `*` wildcards for host labels/ports, or a lone `*`), answers `OPTIONS` preflights, rejects unknown keys / disallowed origins with JSON errors (CORS headers are added to those error responses so the widget can log a useful message), and sets `event.locals.widget = { project, origin }` plus `locals.user` for valid bearer tokens whose user passes `ensureProjectAccess` (see *Roles and project access*). Success responses get `Access-Control-Allow-Origin: <origin>`; credentials are never allowed. New request headers used by the widget must be added to `Access-Control-Allow-Headers` in `src/lib/server/widget-cors.ts`.

Routes (`src/routes/api/widget/[key]/`):

- `GET config` — project flags (including `anonymousFeedbackAllowed`, `openSignups`), viewer (when the bearer token is valid, with `emailNotifications`), dashboard base URL, Turnstile site key, `emailEnabled`. Always available anonymously.
- `GET feedback?scope=page&path=…` (reviewers, if `publicFeedbackVisible`) / `scope=project&status&q` (admins only); `POST feedback` creates an item (zod schema `feedbackCreateSchema` in `validation.ts`; page URL must belong to an allowed origin; anonymous callers must pass Turnstile when configured; optional `mentions` ids are filtered by `resolveMentions`) and returns the detail DTO plus a one-time `uploadToken` when screenshots are enabled, then queues notifications. Signed-in users (any role) post under their account name/email.
- `GET|PATCH|DELETE feedback/[id]` — detail; status change and delete require an admin (`requireAdmin`). `POST feedback/[id]/comments` — reply (non-admins only if `reviewerRepliesEnabled`; anonymous callers pass Turnstile; optional `mentions`), then queues notifications.
- `PUT feedback/[id]/screenshot` — raw image body (PNG/JPEG/WebP sniffed from magic bytes, size capped by `NOTETTE_MAX_SCREENSHOT_BYTES`), authorised by `X-Notette-Upload-Token` within 15 minutes of creation or by an admin token (members use the upload token like reviewers); `GET` streams it for the widget (image tags cannot send bearer tokens, so the widget fetches a blob).
- `auth/login`, `auth/signup`, `auth/requests`, `auth/requests/[id]/poll`, `DELETE auth/session` — see *Authentication*. `POST auth/verify/resend` — new confirmation link for an unverified account.
- `GET mentions` (signed-in only) — people the viewer may @-mention; `PUT notifications { email }` (signed-in only) — per-project email preference. See *Email, notifications and mentions*.

Every route except `config` and `auth/*` starts with `requireWidgetViewer` (401 `sign_in_required` for anonymous requests on projects with anonymous feedback disabled). Visibility rule used everywhere (`src/lib/server/widget-thread.ts`): admins see everything; reviewers (anonymous or member) see a project's feedback only when `publicFeedbackVisible` is on. `/uploads/[id]` (dashboard screenshot URLs, also used in Copy for Agent) follows the same rules using the dashboard cookie, including the sign-in requirement and member access.

Rate limits (`src/lib/server/rate-limit.ts`, in-memory per process) apply to non-admin feedback creation and replies (keyed by user id when signed in, else IP), widget login/sign-up, auth request creation/polling and dashboard login. API handlers are wrapped in `api()` from `http.ts` so `ApiError`/zod errors become JSON `{ error: { message, code, details } }`.

## Storage

`src/lib/server/storage/index.ts` defines `StorageAdapter { put, open, delete }`; `local.ts` implements it on `NOTETTE_UPLOADS_DIR` with atomic writes and key validation (`projects/<projectId>/<uploadId>.<ext>`). `services/uploads.ts` is the only module that touches storage; deleting feedback or projects removes files best-effort before deleting rows. An S3 adapter would implement the same interface and be selected in `getStorage()`.

## Dashboard

Route groups: `(auth)` (login, setup), `(app)` (everything requiring a session; `+layout.server.ts` redirects to `/login?redirect=`, returns 403 for members outside `/` and `/settings/account`, and loads the project list for the sidebar for admins), `(popup)` (minimal layout for the widget authorize page), plus `logout`, `uploads/[id]`, `notette.js`, `api/health`. All mutations are SvelteKit form actions with `use:enhance`, so SvelteKit's origin check provides CSRF protection; there are no cookie-authenticated JSON endpoints. Pages return plain serialisable data (dates as ISO strings; feedback rows mapped with `toSummaryDto`/`toDetailDto` from `services/feedback.ts`).

Pages: overview (`/`; for members a "Your projects" list with site links instead), cross-project list (`/feedback`, filters via query string, 25 per page), project list/settings/try (`/projects/[id]`, `/settings` with the project flags including *Require email verification*, the *Members* card and the personal *Your notifications* card above the danger zone, `/try`), feedback detail with thread (mentions highlighted, reply form with the `@` picker and a hidden `mentions` field), context panels, screenshot, resolve/reopen/delete and Copy for Agent (`/projects/[id]/feedback/[fid]`), account (profile, password, sessions), users (owner-managed; roles owner/admin/member; `unverified` badge and *Mark verified*). The login page uses named actions (`login`, `resend`); `(auth)/verify-email` is the landing page of confirmation links. Author badges show `admin` or `member` (`.badge.admin`/`.badge.member`). Shared components live in `src/lib/components/`; styling is plain CSS in `src/app.css` with light/dark tokens and a responsive shell (sidebar collapses under 900 px).

The login page renders a Turnstile challenge (explicit mode via `src/lib/shared/turnstile-client.ts`) when `turnstileSiteKey` is set in its load data and posts the token as `cf-turnstile-response`. The *Try it* page loads the real widget from the instance's own origin (which must be in the project's allow-list; the page offers to add it) so the full flow can be exercised without deploying. Dashboard pages carry a CSP (`svelte.config.js`): scripts from self and `challenges.cloudflare.com`, frames only from `challenges.cloudflare.com`, connections only to self, inline styles allowed (the widget injects styles into its shadow root), images from self/data/blob.

## Widget

Source: `src/widget/`. Built separately by `vite.widget.config.ts` into a single IIFE bundle `.widget-dist/notette.js` (Svelte 5 components compiled with `css: 'external'`; the `inlineCss` plugin replaces the `__NOTETTE_CSS__` placeholder in `index.ts` with all emitted CSS). `src/routes/notette.js/+server.ts` imports that file with `?raw` and serves it with an ETag, short cache and `Access-Control-Allow-Origin: *`, so the bundle ships inside the SvelteKit build with no separate static hosting. `pnpm run build`/`pnpm run dev` always build the widget first; `pnpm run dev:widget` rebuilds on change.

Runtime structure:

- `index.ts` — reads config from the `<script>` tag (`data-key`, `data-host`, `data-environment|branch|commit|deployment-url`, `data-position`, `data-open`, `data-auto-init`) or `Notette.init(options)`; creates a single `<notette-widget>` host element (`all: initial; position: fixed; z-index` max) appended to `document.body`, attaches an open shadow root with the CSS and mounts `App.svelte` with the controller passed through `mount({ context })`. Exposes `window.Notette` (`init`, `destroy`, `open`, `close`, `comment`, `list`, `focus`) and dispatches `notette:ready`.
- `lib/controller.svelte.ts` — `WidgetController` owns all state (`ui`, a `$state` object) and side effects: config load, page item loading, picking/composing, submit (context capture + screenshot + create + upload), threads/replies/status/delete, panel navigation, focus handling (`?notette=<id>` or `sessionStorage['notette:focus']`), authentication and sign-out, toasts. Components get it via `getContext('notette')`. Access getters: `isAdmin` (owner/admin viewer), `isSignedIn` (any viewer), `requiresSignIn` (project disallows anonymous use and nobody is signed in), `needsTurnstile`, `canSeeFeedback`, `canReply`. Signed-in viewers also get `ui.mentionCandidates` (`loadMentionCandidates`, cleared on sign-out), `ui.accountMenuOpen` (`toggleAccountMenu`) and `setEmailNotifications()`; `ui.emailEnabled` mirrors the server. `submitFeedback`/`reply` accept the `MentionRef[]` from the textarea and send ids. `expand()` and `startPicking()` open the sign-in dialog instead of the toolbar while `requiresSignIn` is true (so `Notette.open()`/`comment()` and deep links behave the same); a pending deep-link focus is kept until sign-in completes. `ui.auth` holds `{ status, mode, url, message }`: `form` is the inline dialog (`openSignIn`, `setAuthMode`, `signInWithPassword`, `signUp`), `verify` the "check your inbox" notice after a sign-up that needs confirmation (`ui.verifyEmail`, `resendVerification`), the other non-idle statuses belong to the dashboard-approval flow (`approveFromDashboard`). A 401 from create/reply clears the token and reopens the dialog (`handleAuthError`); signing out on a sign-in-only project collapses the toolbar.
- `lib/dom.ts` — selector generation (unique id → test-id attributes → short class paths ignoring generated-looking class names → nth-of-type fallback; always verified with `querySelector`), XPath, privacy-conscious element description (no input values), `locateElement` (selector, disambiguated by text, then XPath) and `pinPosition` (element rect × stored relative offset, falling back to recorded page coordinates flagged `approximate`).
- `lib/screenshot.ts` — html2canvas viewport capture (scale capped to ~4 MP, JPEG 0.85, click marker drawn on the image, 12 s timeout, widget host excluded). Never throws; `null` means "submit without screenshot".
- `lib/api.ts` — fetch wrapper for the widget API (`credentials: 'omit'`, bearer token when signed in). `lib/config.ts`, `lib/storage.ts`, `lib/position.ts` are small helpers.
- Components: `Launcher` (bubble → toolbar: Comment, Pins, List, Sign in/avatar, close; the avatar is muted for members and opens `AccountMenu`: identity, email notification toggle when `ui.emailEnabled`, sign out; closes on outside pointer events without blocking them), `Picker` (full-viewport overlay using `document.elementsFromPoint`, hover highlight + label, Esc cancels), `Composer` (anchored popover; shared `MentionTextarea` with the `@` picker opening upwards, name/email for anonymous reviewers, Turnstile when needed, screenshot toggle, Ctrl/⌘+Enter), `Pins` (fixed layer recomputed on scroll/resize/ResizeObserver/`layoutTick`; outline of the selected element), `Thread` (anchored to the pin; bodies rendered through `MentionText`, replies via `MentionTextarea` with Turnstile for anonymous reviewers, `admin`/`member` badges, screenshot thumbnail loaded as a blob, admin actions, Copy for Agent, dashboard link), `Panel` (sidebar list; reviewers see the current page, admins can switch to all pages with status/search filters; selecting an item scrolls to and opens it, or navigates to its page and focuses it on arrival), `AuthDialog` (inline sign-in / sign-up form — sign-up only when `project.openSignups` — with a link to the dashboard-approval flow, the `verify` state and a *Resend confirmation email* link after an `email_unverified` error, plus that flow's waiting/blocked/denied/expired states), `Turnstile` (renders a challenge into an element, exposes `token` via `bind:token` and `reset()` via `bind:this`), `Toast`.

Non-interference rules (keep them when changing the widget): only one host element is added to the page; no global CSS; host-page events are only intercepted while the picker overlay is active (plus a capture-phase Escape handler in that mode); the widget never patches `history`, `fetch` or other globals — SPA navigations are detected via `popstate`/`hashchange`, a debounced MutationObserver and a 1 s path check; `scrollIntoView`/`scrollTo` are only called when the user explicitly focuses an item. The one exception is Turnstile: when the server reports a site key and a challenge is needed, `src/lib/shared/turnstile-client.ts` appends a single `<script data-notette-turnstile>` to the host document's head (Cloudflare's loader, which defines `window.turnstile`). All state is namespaced in `localStorage` under `notette:<key>:…` (token, pin visibility) and `notette:author`.

Feedback DTOs are shared through `src/lib/shared/types.ts`; the widget must never import from `src/lib/server`.

## Email, notifications and mentions

Everything here is optional and switched on by configuration: `config.emailEnabled` is true when `SMTP_HOST` and `EMAIL_FROM` are set (`SMTP_PORT` default 587, `SMTP_SECURE` default true only for 465, `SMTP_USER`/`SMTP_PASSWORD` optional). Without it, nothing is queued, the widget hides the notification toggle, the project setting *Require email verification* is disabled and sign-ups are verified immediately.

Modules (`src/lib/server/email/`): `mailer.ts` wraps a lazily created nodemailer SMTP transport (`sendEmail`, `checkEmailTransport` for the startup log); `templates.ts` holds pure HTML/text rendering (`layout`, `escapeHtml`, `renderBodyHtml` which bolds `@Name` mentions, `renderVerificationEmail`); `digest.ts` builds the batched notification email (`buildDigest`, `digestSubject`) from plain `DigestItem` rows. Templates and the digest builder have no database imports and are unit-tested in `templates.test.ts`; styles are inlined because mail clients ignore stylesheets.

**Notification queue** (`src/lib/server/services/notifications.ts`, table `notifications`): routes call `queueFeedbackNotifications(item, author)` after creating feedback and `queueCommentNotifications(thread, comment, author)` after a reply (widget API and the dashboard reply action). Both are no-ops when email is disabled and never throw. Recipients per event: every owner/admin, every signed-in participant of the thread (feedback author plus reply authors), and mentioned users, who get kind `mention` instead of `feedback`/`comment`. Dropped: the author, accounts without `email_verified_at`, members who are no longer in `project_members`, users with a `notification_mutes` row for the project, and anonymous participants (their addresses are unverified free text). Rows reference feedback/comment with cascade deletes, so deleted items vanish from pending digests.

**Batching**: `startNotificationScheduler()` (called from the `init` hook) runs `flushNotifications()` every 15 s. A recipient is due when their oldest pending row is older than `NOTETTE_EMAIL_BATCH_SECONDS` (default 60); all of their pending rows are then rendered into one digest grouped by project and thread, with "Open on site" links (`siteLinkForFeedback`, i.e. `?notette=<id>`, which the widget focuses on load) and, for admins, dashboard links (only when `NOTETTE_URL` is known). Rows are marked `sent_at` only after SMTP accepted the message; on failure `attempts` is incremented and `next_attempt_at` backs off by 2 min × attempts, giving up after 5 attempts. Hourly maintenance (`cleanupNotifications`) deletes sent rows after 7 days and abandoned ones. The flush is guarded against overlapping runs; the queue lives in the database so a restart loses nothing.

**Preferences**: `notification_mutes (user_id, project_id)`, a row means off. `isEmailNotificationsEnabled`/`setEmailNotifications`. The widget exposes the toggle in the account menu (`AccountMenu.svelte`, opened from the avatar) via `PUT api/widget/[key]/notifications { email }`; the dashboard exposes it to admins in the *Your notifications* card on the project settings page (action `notifications`). `widgetViewer()` (`src/lib/server/widget-viewer.ts`) adds the per-project `emailNotifications` flag to the viewer DTO everywhere the widget receives one.

**Mentions** (`src/lib/shared/mentions.ts`, `src/lib/server/services/mentions.ts`): a mention is `@Display Name` in the text plus a `{ id, name }` reference stored in `feedback.mentions`/`comments.mentions` (jsonb). Who may be mentioned is decided server-side by `listMentionCandidates(user, projectId)`: everyone in `project_members`, plus all owners/admins when the caller is an owner/admin; members only see fellow project members so admin accounts are not enumerable; the caller is excluded; anonymous authors cannot mention. `resolveMentions()` filters submitted ids through that list (max 20), so the client can never target someone outside it. The widget loads candidates from `GET api/widget/[key]/mentions` once signed in (`ui.mentionCandidates`); the dashboard reply form gets them from its page load. The shared `MentionTextarea.svelte` (used by the widget composer/thread and the dashboard reply) opens a picker on `@`, inserts `@Name ` and reports the mentions still present in the text through `bind:mentions` (`activeMentions()`, longest names first so "@Jo Ann" is not also "@Jo"); `MentionText.svelte` highlights mentions when rendering bodies (`segmentMentions()`), and DTOs carry `mentions: string[]` (display names). Mentioned users are notified like participants but their digest entry says "mentioned you"; the per-project mute applies to mentions as well.

**Email verification**: per-project flag `emailVerificationRequired` (project settings, effective only with email enabled). Widget sign-up on such a project creates the member with `email_verified_at = NULL`, stores a hashed 24 h token in `email_verifications` (with the widget origin so the confirmation page can link back), emails `NOTETTE_URL/verify-email?token=…` and answers `202 { verificationRequired: true, email }` instead of a session; the widget shows a "check your inbox" state with a resend button. `verifyEmailToken()` marks the user verified and deletes their tokens; the `(auth)/verify-email` page renders the result. Unverified accounts are rejected by widget login and the dashboard login with `email_unverified` (both offer *Resend confirmation email*, `POST auth/verify/resend` / login action `resend`, rate limited, silent for unknown or verified addresses) and never receive notifications. `users.email_verified_at` defaults to `now()`, so accounts created by admins, `/setup`, bootstrap and every pre-existing account count as verified; owners can also *Mark verified* on the Users page. Expired tokens are deleted by hourly maintenance.

## Copy for Agent

`src/lib/shared/agent-format.ts` renders a `FeedbackDetailDto` (plus optional project name and dashboard link) as Markdown: quoted comment and author, replies, page (URL, path, title, viewport, scroll), target element (tag with attributes, text, selector, XPath, bounding box, click position relative to the element), deployment fields, metadata JSON, screenshot/dashboard links and user agent. Empty sections are omitted. Used by the widget thread header and the dashboard detail page; tested in `agent-format.test.ts`.

## Docker and CI

`Dockerfile`: multi-stage using pnpm via corepack (`deps`: `pnpm install --frozen-lockfile --prod=false` → `build`: `pnpm run build` → `prod-deps`: a clean `pnpm install --prod --ignore-scripts` → slim runtime with `tini`, non-root `node` user, `/data/uploads` volume, healthcheck on `/api/health`). `docker-entrypoint.sh` derives `ORIGIN` from `NOTETTE_URL`. `docker-compose.yml` runs `db` (postgres:16-alpine, volume `notette-db`) and `app` (image `ghcr.io/blunderworks/notette`, `build: .` for local builds, volume `notette-uploads`). `.github/workflows/ci.yml` runs check/test/build and a Docker build on pushes and PRs; `release.yml` publishes multi-arch images on `v*.*.*` tags with semver + `latest` tags.
